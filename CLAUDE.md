# CLAUDE.md

Public **stdio MCP server** (npm: `postfast-mcp`, plus `postfast` from `packages/postfast/`, which runs the same server) over PostFast's pf-api-key REST API — and the home of the **shared tool catalog** (`src/core`, exported as `postfast-mcp/core`). The deployed remote twin `../social-schedule-mcp` (mcp.postfa.st) consumes the catalog too — its adapter landed 2026-08-05 (`src/mcp/mcp.service.ts` + `gateway.adapter.ts` import `postfast-mcp/core`), and a release here auto-bumps it (Release step 3).

## Rules

- **Source of truth is the backend**: `../social-schedule-service` — its `docs/periphery.md` holds the constellation map (repos, verify commands, release channels).
- **Tool descriptions ARE the API** — models discover fields only from descriptions/schemas, so wording changes are behavior changes. Keep them accurate against the BE REST responses.
- **The catalog IS the single source**: every tool (schema + description + title + annotations + outputSchema + binding) lives ONLY in `src/core/tools/`. Never author tool text anywhere else; both bindings render from it.
- stdio surface stability: `scripts/parity-diff.mjs` diffs a published version against the local build (initialize + tools/list over real stdio). Run it before any release that touches the catalog.
- **One remote surface, always confirm-gated**: every hosted session, whatever the client, gets the same catalogue. Posts are created held and publish only through `approve_posts`. Each comment operation is its own pair of tools, a read-only preview and the tool that carries it out with a token from that preview only, each after the user's yes: `preview_comment_reply` → `reply_to_comment`, `preview_private_reply` → `send_private_reply`, `preview_comment_deletion` → `delete_comment`. No remote tool picks between operations with a parameter. There is no ungated remote variant of any description, schema, annotation or server instruction: text that lets a model publish, approve, reply, delete, hide, email or point a webhook endpoint at a URL without the user's yes exists only on stdio, and `test/confirm-gate.test.mjs` checks the remote wording and the one-operation-per-tool rule. The host must pass `confirmGate` (without it the six comment tools are left out and a log line says so). `test/remote-surface.test.mjs` pins instructions + tools/list to `test/snapshots/remote-surface.json`; any change fails until `UPDATE_SNAPSHOT=1 npm test`, and the snapshot diff belongs in the PR, since it is what every hosted client and every directory reviewer sees.
- **OAuth scopes (remote only)**: every remote tool declares `scopes`, exactly what the backend's MCP gateway checks for its call (`../social-schedule-service/src/mcp-gateway/mcp-gateway.controller.ts`, through the gateway command the host sends), and lists them as `securitySchemes` at the top level of tools/list and in `_meta.securitySchemes`. They are a hint for clients; the backend enforces scopes on every call. `test/oauth-scopes.test.mjs` pins the table, so a new tool or a backend scope change updates it. With `RegisterToolsOptions.scopeChallenge`, an `InsufficientScopeError` thrown by the port becomes an `insufficient_scope` challenge in the result's `_meta["mcp/www_authenticate"]`, asking for the token's granted scopes (from the request's `authInfo`) plus the tool's.
- **Calendar app (opt-in, remote only)**: `src/core/app.ts`, `src/core/tools/app.ts` and the view in `view/` (vite single-file build to `dist/view/index.html`, read at runtime). A host turns it on with `BuildToolsOptions.app` (for every hosted session; its tools are app-only, hidden from the model); without it every surface stays byte-identical, and `test/app.test.mjs` checks that. `@openai/mcp-extensions` and `@modelcontextprotocol/ext-apps` are devDependencies only (type-only imports checked with `satisfies`, and bundled into the view). Never make them runtime dependencies: the host's pnpm release-age gate rejects fresh versions even as transitive dependencies, and the OpenAI package needs Node 22 and pins zod exactly. Tool `icons` (and every remote tool's top-level `securitySchemes`) reach tools/list by wrapping the SDK's tools/list handler, so re-check them on SDK bumps. `scripts/app-preview.mjs` serves the app with fixture data for ext-apps' basic-host (scenarios include several workspaces, a "many" one with 30 workspaces and 40 accounts, and a "single" one); `appViewHtml()` reads the view once, so restart the preview after `npm run build`.
- **Directory plugin `plugins/postfast/`**: skills plus a `.mcp.json` pointing at the hosted connector (`https://mcp.postfa.st/mcp`), listed in the Claude directory separately from the root plugin. Its skills are written for the remote surface, so a catalog change that renames or removes a tool, or changes a limit in the server instructions, updates the skills in the same PR; `test/directory-plugin.test.mjs` fails until it does. The skills name no client app (other clients' packages ship the same `skills/` folder); the test enforces that too. Character limits live only in `skills/schedule-posts/references/platform-rules.md`. The folder is outside the npm package (`files`) and the `.mcpb` (`.mcpbignore`), so a plugin-only change needs no changeset or npm release. Its `version` is independent of the package version and not stamped: raise it by hand on every change to the folder. The directory reads only this folder, from the branch or tag tracked in the developer portal, which is currently `main`: a scheduled check finds each new `plugin.json` version a few hours after it merges and reviews it, so merging a version bump submits it (Release step 4). Its README section "What the PostFast tools can do" says in plain words what the connector's tools can publish, send, delete or change access to. The directory refuses a version whose README and manifest don't (DP_TAG_BOUNCE), so a catalog change that adds or changes such a tool updates that section in the same PR.
- **Cursor plugin `.cursor-plugin/plugin.json`**: Cursor looks for `.cursor-plugin/plugin.json`, then `.claude-plugin/plugin.json`, then a root `plugin.json`, so this file decides what Cursor loads from the repository root. It launches the same pinned server as the Claude Code plugin, declares `POSTFAST_API_KEY` as a variable that Cursor asks for at install, and uses the root `skills/` and `assets/logo.png`; `test/cursor-plugin.test.mjs` keeps it in step. A root Agent Plugins `plugin.json` would be shadowed by the Claude manifest in Cursor, and the Agent Plugins spec has no way to pass an API key to a stdio server.
- **npm `postfast` (`packages/postfast/`)**: the bare name on npm, so that `npx postfast` and `npm install postfast` reach this server. Its bin only imports `postfast-mcp`, whose main export is the stdio server, and it depends on `postfast-mcp` pinned exactly at its own version (both stamped). It is not a workspace, so the root `npm ci` and lockfile ignore it, and it stays out of the root package (`files`) and the `.mcpb` (`.mcpbignore`). Running it with no arguments must keep starting the MCP server, since the registry entry and client configs run `npx -y postfast`; a CLI added later goes behind subcommands. `test/npm-alias.test.mjs` checks the pin, the tarball and the served surface over real stdio.
- **MCP Registry name `st.postfa/postfast`**: DNS-verified on postfa.st. The apex TXT record `v=MCPv1; k=ed25519; p=<public key>` matches `MCP_REGISTRY_PRIVATE_KEY`, a secret of the `mcp-registry` environment (deployable from `main` and `v*.*.*` tags only). The entry lists npm `postfast`, and the registry publishes a version only when that npm version's `mcpName` equals the entry name, so both packages carry `"mcpName": "st.postfa/postfast"`. Up to 0.15.3 the entry was `io.github.peturgeorgievv-factory/postfast-mcp`; the registry job marks it deprecated (not deleted, so its versions stay listed). Registry names never move, so a different name means a new entry again.
- **Workflow security**: `release.yml`'s dispatch authenticates as the release-bot GitHub App (`RELEASE_BOT_APP_ID` + `RELEASE_BOT_PRIVATE_KEY`; the private key is the critical credential) — it mints a short-lived token scoped to social-schedule-mcp only. The registry job holds the other long-lived credential, `MCP_REGISTRY_PRIVATE_KEY`; whoever has it can publish versions of `st.postfa/postfast`, which may list any npm package that declares that `mcpName`. It is an environment secret, read only by the login step, and the `mcp-publisher` binary it is handed is pinned and signature-checked. Rotate it by putting a new public key in the TXT record, replacing the secret, then removing the old record. Reference secrets ONLY on the step that uses them, never job/workflow level. This repo must NEVER gain a `pull_request_target` workflow that checks out PR code, and no secret-bearing workflow may interpolate PR-controlled strings (titles, branch names, bodies).
- Never commit with AI/Claude attribution or Co-authored-by.

## Release (tag-triggered — no npm token; one registry signing key)

1. Every behavior-changing PR adds a `.changeset/*.md` (patch/minor + summary).
2. To release: `npm run version` (changesets computes the bump + CHANGELOG, `scripts/stamp-versions.mjs` stamps manifest.json, server.json, both `.claude-plugin/` files, `.cursor-plugin/plugin.json`, `packages/postfast/package.json` (version and pin), `src/stdio/index.ts`, package-lock.json) → review the diff → commit ("…, bump to X" style).
3. **Pushing the tag is the publish button**: `git tag vX.Y.Z && git push origin main vX.Y.Z`. `release.yml`'s `release` job then publishes `postfast-mcp`, then `postfast`, to npm (trusted publishing/OIDC; each skips a version npm already has), and a GitHub Release with the `.mcpb` attached. A tag that doesn't match the stamped versions fails fast. Its `registry` job then signs in with the DNS key and publishes server.json. The `catalog-release` repository_dispatch then wakes `social-schedule-mcp`'s `catalog-bump.yml`, which waits for npm to serve the version, pins it exactly, commits `[skip ci]`, and triggers its Docker build — the host picks up the new catalog with nothing further to do here. A failed job? "Re-run failed jobs" resumes it. To publish main's server.json alone, run the workflow by hand (`workflow_dispatch` runs only the registry job).
4. **Directory plugin release** (`plugins/postfast/`, separate from npm): merge a PR that changes the folder and raises its `plugin.json` version. The portal tracks `main` (plugin → Settings → Tracked branch or tag), so its scheduled check picks up the new version within hours, runs validation, directory policy and the security scan, and publishes a version that passes. After a refusal the portal asks for a new version, so a fix raises the version again. Tag the merge commit `postfast-plugin-v<that version>` (a new lightweight tag; never move an existing one) for the ChatGPT package's sync: `git tag postfast-plugin-vX.Y.Z <merge sha> && git push origin refs/tags/postfast-plugin-vX.Y.Z`. If the skills depend on a catalog change, release `vX.Y.Z` (step 3) and wait for the hosted server to redeploy before merging the plugin change. `postfast-plugin-v*` tags never trigger `release.yml`, which matches `v*.*.*` only.
