# CLAUDE.md

Public **stdio MCP server** (npm: `postfast-mcp`) over PostFast's pf-api-key REST API — and the home of the **shared tool catalog** (`src/core`, exported as `postfast-mcp/core`). The deployed remote twin `../social-schedule-mcp` (mcp.postfa.st) consumes the catalog too — its adapter landed 2026-08-05 (`src/mcp/mcp.service.ts` + `gateway.adapter.ts` import `postfast-mcp/core`), and a release here auto-bumps it (Release step 3).

## Rules

- **Source of truth is the backend**: `../social-schedule-service` — its `docs/periphery.md` holds the constellation map (repos, verify commands, release channels).
- **Tool descriptions ARE the API** — models discover fields only from descriptions/schemas, so wording changes are behavior changes. Keep them accurate against the BE REST responses.
- **The catalog IS the single source**: every tool (schema + description + title + annotations + outputSchema + binding) lives ONLY in `src/core/tools/`. Never author tool text anywhere else; both bindings render from it.
- stdio surface stability: `scripts/parity-diff.mjs` diffs a published version against the local build (initialize + tools/list over real stdio). Run it before any release that touches the catalog.
- **One remote surface, always confirm-gated**: every hosted session, whatever the client, gets the same catalogue. Posts are created held and publish only through `approve_posts`; comment replies, private replies and deletions go through `prepare_inbox_action` / `confirm_inbox_action`, each after the user's yes. There is no ungated remote variant of any description, schema, annotation or server instruction: text that lets a model publish, approve, reply, delete, hide or email without the user's yes exists only on stdio, and `test/confirm-gate.test.mjs` checks the remote wording. The host must pass `confirmGate` (without it the two confirm tools are left out and a log line says so). `test/remote-surface.test.mjs` pins instructions + tools/list to `test/snapshots/remote-surface.json`; any change fails until `UPDATE_SNAPSHOT=1 npm test`, and the snapshot diff belongs in the PR, since it is what every hosted client and every directory reviewer sees.
- **Calendar app (opt-in, remote only)**: `src/core/app.ts`, `src/core/tools/app.ts` and the view in `view/` (vite single-file build to `dist/view/index.html`, read at runtime). A host turns it on with `BuildToolsOptions.app` (for every hosted session; its tools are app-only, hidden from the model); without it every surface stays byte-identical, and `test/app.test.mjs` checks that. `@openai/mcp-extensions` and `@modelcontextprotocol/ext-apps` are devDependencies only (type-only imports checked with `satisfies`, and bundled into the view). Never make them runtime dependencies: the host's pnpm release-age gate rejects fresh versions even as transitive dependencies, and the OpenAI package needs Node 22 and pins zod exactly. Tool `icons` reach tools/list by wrapping the SDK's tools/list handler, so re-check them on SDK bumps. `scripts/app-preview.mjs` serves the app with fixture data for ext-apps' basic-host.
- **Directory plugin `plugins/postfast/`**: skills plus a `.mcp.json` pointing at the hosted connector (`https://mcp.postfa.st/mcp`), listed in the Claude directory separately from the root plugin. Its skills are written for the remote surface, so a catalog change that renames or removes a tool, or changes a limit in the server instructions, updates the skills in the same PR; `test/directory-plugin.test.mjs` fails until it does. The skills name no client app (other clients' packages ship the same `skills/` folder); the test enforces that too. Character limits live only in `skills/schedule-posts/references/platform-rules.md`. The folder is outside the npm package (`files`) and the `.mcpb` (`.mcpbignore`), so a plugin-only change needs no changeset or npm release. Its `version` is independent of the package version and not stamped: raise it by hand on every change to the folder. The directory reads only this folder, from the `postfast-plugin-v*` tag set as its tracked tag in the developer portal, so merging to `main` alone publishes nothing there (Release step 4).
- **Cursor plugin `.cursor-plugin/plugin.json`**: Cursor looks for `.cursor-plugin/plugin.json`, then `.claude-plugin/plugin.json`, then a root `plugin.json`, so this file decides what Cursor loads from the repository root. It launches the same pinned server as the Claude Code plugin, declares `POSTFAST_API_KEY` as a variable that Cursor asks for at install, and uses the root `skills/` and `assets/logo.png`; `test/cursor-plugin.test.mjs` keeps it in step. A root Agent Plugins `plugin.json` would be shadowed by the Claude manifest in Cursor, and the Agent Plugins spec has no way to pass an API key to a stdio server.
- **Workflow security**: `release.yml`'s dispatch authenticates as the release-bot GitHub App (`RELEASE_BOT_APP_ID` + `RELEASE_BOT_PRIVATE_KEY`; the private key is the critical credential) — it mints a short-lived token scoped to social-schedule-mcp only. Reference secrets ONLY on the step that uses them, never job/workflow level. This repo must NEVER gain a `pull_request_target` workflow that checks out PR code, and no secret-bearing workflow may interpolate PR-controlled strings (titles, branch names, bodies).
- Never commit with AI/Claude attribution or Co-authored-by.

## Release (tag-triggered — CI holds no credentials)

1. Every behavior-changing PR adds a `.changeset/*.md` (patch/minor + summary).
2. To release: `npm run version` (changesets computes the bump + CHANGELOG, `scripts/stamp-versions.mjs` stamps manifest.json, server.json, both `.claude-plugin/` files, `.cursor-plugin/plugin.json`, `src/stdio/index.ts`, package-lock.json) → review the diff → commit ("…, bump to X" style).
3. **Pushing the tag is the publish button**: `git tag vX.Y.Z && git push origin main vX.Y.Z`. `release.yml` then publishes npm (trusted publishing/OIDC), the MCP Registry (github-oidc), and a GitHub Release with the `.mcpb` attached. A tag that doesn't match package.json fails fast. The `catalog-release` repository_dispatch then wakes `social-schedule-mcp`'s `catalog-bump.yml`, which waits for npm to serve the version, pins it exactly, commits `[skip ci]`, and triggers its Docker build — the host picks up the new catalog with nothing further to do here. Registry hiccup? Re-run via the workflow's manual `workflow_dispatch` (registry-republish job).
4. **Directory plugin release** (`plugins/postfast/`, separate from npm): merge a PR that changes the folder and raises its `plugin.json` version, then tag the merge commit `postfast-plugin-v<that version>` (a new lightweight tag; never move an existing one) and push it: `git tag postfast-plugin-vX.Y.Z <merge sha> && git push origin refs/tags/postfast-plugin-vX.Y.Z`. The maintainer then sets that tag as the tracked tag in the developer portal (plugin → Settings → Tracked branch or tag; not possible while the plugin is with a reviewer), and the directory scans and publishes it. If the skills depend on a catalog change, release `vX.Y.Z` (step 3) first and wait for the hosted server to redeploy. `postfast-plugin-v*` tags never trigger `release.yml`, which matches `v*.*.*` only.
